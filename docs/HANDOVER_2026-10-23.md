# 1. 專案概要

## 專案目的

以 Google Trends 台灣熱搜、熱搜附帶的新聞與股價建立**事件研究（event study）**流程，觀察熱門主題出現後相關股票的市場反應。屬於**作品集與研究驗證專案**，不預測股價、不產生交易訊號、不構成投資建議。研究期間從 **2026-08-21** 起（Dashboard 只使用此日之後的資料）。

## 研究假說（README）

1. 搜尋熱度明顯增加後，相關股票未來數個交易日出現正報酬的比例可能提高。
2. 正面新聞的平均股價反應可能大於負面新聞。
3. AI、科技、金融、能源、生技、消費及半導體等主題可能有不同反應速度。
4. 搜尋熱度高峰與 MA20、MA60 均線突破之間可能存在時間差。

事件定義（符合任一）：當日搜尋熱度較前 7 日平均增加 ≥ 50%；或當日新聞 ≥ 3 篇且達前 7 日平均 2 倍以上。非交易日事件對齊至下一個交易日。事件日期使用 RSS 的 `published_at`。

**依賴關係（重要）**：假說 1、4 依賴 `google_trends_history`（pytrends 歷史熱度）；假說 2 依賴新聞情緒（Gemini）；假說 3 依賴關鍵字主題分類（Gemini + 規則）。所有假說都依賴 `stocks` 股價與 `theme_mapping` 主題→股票對應。

## 系統架構

- 單機 Windows 10 桌機，所有資料存在專案根目錄 SQLite `data.db`（不依賴雲端資料庫）。
- 4 個 Windows 工作排程器工作（`\Trends\`），每個都是「執行一次即結束」的批次檔，透過 `deploy\run_hidden.vbs` 以隱藏視窗執行。
- Streamlit Dashboard（`app.py` → `trends.dashboard.main`）唯讀查詢 `data.db`，三頁：專案介紹、市場雷達、事件研究。事件研究結果在開頁時即時計算，不寫入資料庫。
- 每日健康報告（唯讀）輸出 `logs\health_report.md`。

## Gemini 使用方式

- 所有呼叫經 `keyword_classification._generate_json(client, models, prompt, task, items)` → `get_gemini_limiter().call(lambda model: client.models.generate_content(model=model, ...), models)`，`response_mime_type="application/json"`。
- 四個用途（task 名稱）：`entity`（Entity Resolution）、`keyword`（關鍵字分類）、`auto_quality`（未分類自動分類）、`news`（新聞情緒 + 事件類型）。
- 模型順序（`gemini_control.DEFAULT_MODELS`）：`gemini-3.6-flash` → `gemini-3.8-flash` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite`。可在 `.env` 用 `GEMINI_MODELS=a,b,c` 覆寫。
- 重試政策：每日配額 429 → 立即換下一個模型；每分鐘 429 → 依 `retryDelay` 等待，最多重試 3 次後換模型；5xx → 等 10 秒重試 1 次後換模型；404 → 換模型；某模型放棄後本次執行不再使用；全部放棄或累計等待超過 30 分鐘 → 本次執行停止所有 Gemini 步驟（`GeminiStopped`），非 Gemini 步驟照常。
- 每次 ETL 上限（`run_etl.bat`）：`--keyword-limit 400 --news-limit 1000`；自動分類 `limit=100`；每個請求 150 筆。
- 續跑：`data.gemini_progress.json`（資料庫旁）記錄各 task 已回答的項目（目前 entity 2,072、keyword 50），避免重送「回答過但仍在待處理清單」的項目。
- ETL 結束時在 `logs\etl.log` 印出 `Gemini Stats` 區塊（`Requests`、`Models`、`Processed`、`Skipped`、`429 Count`、`503 Count`、`Wait Time`、`Stopped`），健康報告解析這個區塊。
- 沒有金鑰時：關鍵字改用規則分類（標記 `fallback`），新聞情緒保留未分析，**不會偽造結果**。

## Google Trends 使用方式

- **RSS**（`rss_collector`）：feed 只放最新約 10 筆熱搜，按 pubDate 由新到舊排列；pubDate 落在每 10 分鐘的格點上（已確認）。
- **歷史熱度**（`trend_history_collector`，ETL 第 4 步）：對 `theme_mapping` 中啟用的主題關鍵字查近 90 天日熱度；`timeout=(10, 30)`；捨棄 `isPartial`（所以正常時最新日 = 昨天）；已更新到昨天的跳過；輪替順序為最久未更新優先；**遇到第一個 429 就停止整個步驟**（不重試，避免延長封鎖），ETL exit code = 3。

# 6. 目前已知問題（依嚴重度排序）

## P1. Google Trends 歷史熱度（pytrends）幾乎停擺 — 嚴重度：高

- **問題描述**：10/19 起每次 ETL 成功 0～10 個關鍵字，熱度覆蓋率從 64% 降到 4.2%，最新熱度日停在 10/21，451 個關鍵字停在 10/16～10/17。
- **根本原因分析**：pytrends 是非官方介面、已停止維護，Google 對同一 IP 的 429 封鎖越來越嚴格（推論；確認的是 429 本身）。每天 4 次 ETL 都會去碰 Google，可能讓封鎖一直延續（推論，未驗證）。目前設計在第一個 429 就停止，本身是正確的保護。
- **是否已確認**：現象已確認（log + 資料庫）；原因屬推論。
- **影響範圍**：假說 1、4 所需的熱度資料；`docs/data_pipeline.md` 估計約 90% 的事件來自「搜尋熱度上升」，事件研究的事件數會大幅減少；市場雷達熱度變化停滯。缺口在 90 天內可回補。
- **解決方案（待評估）**：(a) 減少每天查詢次數（例如每天 1 次、固定在 429 機率低的時段），並拉長 `request_delay`；(b) 每次只查有對應股票的關鍵字（337 個中優先）；(c) 每次限制最多 N 個關鍵字，避免把每天的「額度」一次用光；(d) 評估其他資料來源（例如 Google Trends 官方 API 測試版，若可取得）；(e) 先記錄每次第一個 429 前成功的數量與時段，用數據決定策略。
- **優先級**：最高（研究資料可信度的主要瓶頸）。

## P2. 股價：theme_mapping 中 81 個股票代號從未下載股價 — 嚴重度：高

- **問題描述**：`theme_mapping` 資料表有 145 個不同的 `stock_id`，但 `stocks` 只有 75 檔；**81 個代號沒有任何股價**（例如 006208、00662、1201、2312、2328、2337…）。
- **根本原因分析（已確認）**：**【程式落差】** `stock_collector.DEFAULT_STOCKS = sorted(set(get_stock_pool()) | set(load_theme_mapping()["stock_id"]))` 只讀 CSV（`keyword_theme_mapping.csv`、`theme_mapping.csv`），但 ETL 的 Gemini/Entity Resolution 會把新的股票代號寫進 `theme_mapping` **資料表**（`_upsert_theme_rows`），股價收集器不會讀資料表。
- **影響範圍**：對應到這 81 檔的關鍵字事件都算不出報酬（Dashboard 會顯示資料不足），等於 AI 辨識出的新公司全部無法進入事件研究。
- **解決方案**：股票池改為 CSV ∪ `theme_mapping` 資料表中 active 的 `stock_id`；新增的代號由既有邏輯回補 5 年。要注意 yfinance 請求數會從 75 增加到約 150，執行時間約加倍（目前 35 秒）。
- **優先級**：高（修改小、效果確定）。

## P3. 股價：上櫃股票一律轉成 `.TW`，12 檔永遠抓不到 — 嚴重度：中高

- **問題描述**：3083、3086、3324、3546、4128、4147、5478、5903、6180、6274、6547、8044 每次都是「possibly delisted」。
- **根本原因分析（已確認）**：**【程式落差】** `stock_collector.to_yfinance_ticker()` 對純數字代號一律加 `.TW`；這些是上櫃（TPEx）股票，yfinance 需要 `.TWO`。實測 `3324.TW` 回 404，`3324.TWO`、`8044.TWO`、`6180.TWO` 都有 10/22 資料。
- **影響範圍**：遊戲（智冠 5478、橘子 6180、網龍 3083、華義 3086、宇峻 3546）、生技（中天 4128、中裕 4147、高端 6547）、電商（網家 8044）、消費（全家 5903）、科技（雙鴻 3324、台燿 6274）等主題的代表股沒有股價。P2 的 81 檔中可能也有上櫃股票。
- **解決方案**：`.TW` 失敗（空資料）時改試 `.TWO`，或維護上市/上櫃清單；`stocks.stock_id` 仍存不帶後綴的代號，維持一致。

5. **統計**：`GeminiStats.model_requests`，`Gemini Stats` 報告多一行 `Models: <model> <n>, ...`（有請求時才出現）。

# 10. AI 接手須知

## 容易踩坑的地方

1. **時區**：資料庫一律 UTC（`fetched_at`、`published_at`、`created_at`、`classified_at`）；log 檔是台北時間；健康報告以台北日計算。查詢某個「台北日」的資料要先減 8 小時。
2. **主控台編碼 cp950**：印中文或 emoji 會 `UnicodeEncodeError`。用 `PYTHONIOENCODING=utf-8`，或在腳本開頭 `sys.stdout.reconfigure(encoding='utf-8')`（`python -I` 會忽略 `PYTHON*` 環境變數）。
3. **測試用 unittest**：`.venv\Scripts\python.exe -m unittest discover -s tests`。沒有安裝 pytest。
4. **修改 RSS Collector 排程需要系統管理員權限**，其他三個不用。只改單一屬性時用 `Set-ScheduledTask -Action` 或 `-Trigger`，不要重建整個工作（會改變觸發時間點與歷史）。
5. **排程動作必須經過 `run_hidden.vbs`**，否則每次都會跳出 cmd 視窗（使用者明確抱怨過）。新增排程時要沿用 `wscript.exe //B //Nologo "<vbs>" "<bat>"`。
6. **Gemini 免費額度很小**：每模型每天 20 個請求，**失敗的請求也算**。手動測試會吃掉排程的額度；不要用大量小請求「試試看」。看錯誤訊息裡的 `model:` 判斷是哪個模型的額度。
7. **模型名稱不等於獨立模型**：3.5-flash 共用 3.6-flash 的額度，3.7-flash 會轉到 3.8-flash，2.5 系列對這個帳號是 404。改模型清單前要實測。
8. **`data.gemini_progress.json`** 記錄已回答的項目，刪除只會造成重送，不會壞資料。但它是續跑機制的一部分，不要當垃圾檔清掉。
9. **ETL exit 3 是預期內的**（pytrends 429），不是程式錯誤；健康報告 exit 1 代表有元件 FAIL。
10. **批次檔的 echo 重導向**要把 `>>` 放在行首（`>> file echo ...`），否則 `exit %RC%>> file` 會變成 `0>> file`（`run_*.bat` 有註解說明）。
11. **不要使用任何模組的 `--schedule`**：那是 APScheduler 常駐模式，會和工作排程器重複觸發。
12. **`.env` 內有真實帳密**（Gemini、Snowflake、DB）：不要讀出值、不要 commit、不要寫進文件。
13. **資料庫寫入衝突**：SQLite 同時寫入可能 `database is locked`；排程刻意錯開（股價 18:30、ETL 02/08/14/20 時）。新增排程時要避開這些時間。
14. **`stocks.stock_id` 不帶後綴**（`2330`、`NVDA`），轉換只發生在 `to_yfinance_ticker`。
15. **這台電腦的工作只在使用者登入時執行**（`LogonType Interactive`）；登出或關機期間 RSS 的資料無法回補。

## 哪些歷史決策不要被推翻（以及原因）

| 決策 | 原因 |
|---|---|
| 每個工作「執行一次即結束」，由 Windows 工作排程器觸發 | 常駐程序在關閉終端機或重開機後會中斷；排程器有錯過補跑、不重疊執行 |
| RSS 冪等寫入（唯一鍵 `(keyword, published_at)`，`fetched_at` 保留第一次觀察） | 可重跑、不重複；`fetched_at` 可用來分析「第一次看到」的時間 |
| 資料庫存 UTC，讀取端轉台北（C6） | 舊資料曾把太平洋時間當本地時間存，造成日期錯位；P0-2 已遷移 |
| 事件日期用 `published_at`（Google 的時間），不是抓取時間 | 與抓取頻率無關，也是降頻到 20 分鐘的前提 |
| 沒有 Gemini 金鑰或 Gemini 失敗時，**不偽造新聞情緒** | 研究可信度；寧可標示「未分析」 |
| pytrends 遇到**第一個 429 就停** | 繼續打只會延長封鎖 |
| Gemini 續跑紀錄、每批完成即寫入 | 額度隨時會用完，要能從中斷處繼續 |
| 隱藏視窗啟動器（`run_hidden.vbs`） | 使用者要求，不影響 exit code |
| RSS 每 20 分鐘 | 以 7 天資料推算漏抓約 1%，抓取次數減半（第 5 節）。要改回更高頻率請先看實際漏抓 |

| 研究期間從 2026-08-21 開始 | Dashboard 與研究摘要的固定起點 |
| 專案定位為研究與作品集，不產生交易訊號 | README 明訂；Alpha 分數只是排序，不是建議 |
